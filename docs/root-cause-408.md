# 408 的根因：提交环境判定，不是负载

## 症状

- 提交生成任务恒定返回 `408`，body 是 `{"error_code":"timeout_error","message":"System under load, please retry."}`
- 响应头 `x-colligo-timeout: 0.0`
- 票本身字段齐全（`ftr` / `ark` / `sid` / `bfp` 都在），铸票耗时正常
- 换 5 个不同美国住宅出口、换账号、换请求体，结果都是 408
- 不带票直接打边界 → `403 ErrMissingAPIKey`（说明服务可达，不是网络/宕机）

「负载高」是文案，`x-colligo-timeout: 0.0` 说明它在**准入阶段**就被判掉了，根本没进排队。

## 判定矩阵（实测）

唯一变量是 `x-arp-session-id`（会话票）的**铸造方式**：

| 铸造方式 | 铸造出口 | 票的质量 | 提交结果 |
| --- | --- | --- | --- |
| HEADED（fingerprint-chromium + Xvfb） | 任意（机房直连也行） | 好 | 200 |
| HEADLESS + 住宅代理 | 住宅 | 中（时好时坏） | 200 / 408 交替 |
| HEADLESS + 直连/机房 | 机房 | 坏 | 408 |
| 无 arp / 伪造 arp（纯协议算出来） | — | 无 | 恒定 408 |

结论：**票不是「算」出来的，是「跑」出来的。** 纯协议复刻 Arkose/Forter/BFP 的数值即使格式正确，
也缺少浏览器环境里那些隐式信号（渲染时序、WebGL/Canvas、真实事件序列等），被判定为不可信环境。

## 对照实验（如何自证）

固定账号、固定出口、固定请求体，只换票：

```
同一批 30s 内新采账号 + 同一住宅 session-<id> 出口：

  x-arp-session-id = 采号票（纯协议/无头铸）   → 3/3  HTTP 408  ct=0.0
  x-arp-session-id = 有头铸的新票              → 3/3  HTTP 200  → job IN_PROGRESS
                                                  → 轮询 result href 拿到 presignedUrl
                                                  → 下载 217KB JPEG 成功
```

这一步做完就可以确定：问题在票，不在账号池、代理池、请求体或上游可用性。

## 为什么「以前能跑」

早期判定较宽，纯协议票也能过，于是「采号时顺手铸一张票、复用到底」是最省事的做法。
平台在 2026-11 收紧后，所有依赖纯协议票的链路同时失效，表现为「服务全挂但票看起来正常」——
这也是最容易误判成「上游挂了 / IP 脏了 / 账号被封了」的时刻。

## 修复后的稳定状态（实测）

- 铸票 ~4s，服务内 60s 缓存，48 并发首波只铸 1 枚
- 网关出图：`200`，40s 左右（含生成耗时），3 并发全 200
- 客户侧入口经反代：`200`，43s，presigned URL 下载 1.7MB JPEG
- 熔断器 `open=false`，`window_ct0_hits=0`

## 反模式清单

- ❌ 看到 408 就换代理 / 换 IP 段 —— 5 个不同住宅段全 408，说明与出口无关
- ❌ 认为「票四字段齐全 = 票可用」 —— 格式正确 ≠ 环境可信
- ❌ 复用采号票 —— 采号链是纯协议/无头，天然在「不可信」档
- ❌ 把 sidecar 改成 headless 省内存 —— 立刻回到全量 408
- ❌ 手工重启 sidecar 后忘了检查 `/health` 里的 `headless` 字段
